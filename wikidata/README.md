# Technical Specification of the Homonym Disambiguation Pipeline (Wikidata)

This repository consolidates the process flow for extraction, structuring, modeling, and statistical validation of data originating from Wikidata, aiming to resolve ambiguities in nominal entities (homonyms). The architecture described below substantiates the experiments conducted for the paper submitted to SBBD 2026.

The pipeline execution is strictly sequential. The processes start from the ingestion of the raw structured dump and progress to the evaluation of ranking models, passing through critical stages of memory optimization and feature engineering.

---

## Operational Structure and Project Files

The pipeline was segmented into three main logical phases. The scope, inputs, methods, and artifacts generated by each component are detailed below.

### Phase 1: Data Ingestion and Standardization

This phase focuses on dimensionality reduction and the translation of Wikidata metadata into a viable format for exploratory analysis and feature extraction.

* processamento01 dump.ipynb
* * Objective: Initial processing of the compressed dump (`wdump-5306.nt.gz`).


* * Operations: Performs the selective reading of structured triples, filtering entities based on pre-mapped properties of interest (e.g., `P21` for gender, `P27` for nationality, `P569` for birth date, and kinship identifiers). Entities without relevant topological connections or sufficient metadata are discarded in the process.


* * Output: Preliminary CSV file, significantly reduced in volume, containing the base matrix of entities.




* processamento02 mapeamento.ipynb
* * Objective: Conversion of alphanumeric identifiers (QIDs).


* * Operations: Scans the base generated in the previous step to compile a dictionary of unique QIDs. Performs systematic queries to retrieve the textual labels associated with each code, replacing them in the original dataset.


* * Output: Dataset with lexical categorical variables (e.g., locations and professions described in text, instead of identifiers).




* processamento03 tratamento.ipynb
* * Objective: Sanitization and integrity analysis of the database.


* * Operations: Normalizes column nomenclature, removing technical suffixes. Handles anomalous data structures (such as empty lists resulting from the mapping phase) and employs completeness analyses using the `missingno` library to generate sparsity matrices.


* * Output: Canonical and sanitized tabular database, ready for relational modeling.





### Phase 2: Domain Structuring and Feature Engineering

The logical core of the experiment resides in this phase, where the generic database is transformed into a dataset focused on entity resolution, defining the topology of ambiguous pairs.

* processamento04 homonimos.ipynb [CRITICAL COMPONENT]
* * Objective: Structural definition of the nominal ambiguity problem.


* * Operations: This module is responsible for identifying and grouping sets of distinct entities that share the same identification string (name). The script computes data intersections, consolidates information dictionaries per entity, and generates the primary statistical profile of the problem. It calculates the total amount of viable pairs, the mean and standard deviation of homonyms per grouped name, in addition to summarizing the volume of unique variables present (distribution of professions, nationalities, and addresses within the scope of the experiment).


* * Output: `wikidata_pessoa_homonimo.jsonl` file, containing the relational and hierarchical grouping necessary for the formulation of candidates in the recommendation/ranking models.




* processamento05 pessoas.ipynb
* * Objective: Structural optimization and redundancy reduction.


* * Operations: Acts as a computational deduplication process. Extracts from the grouping JSONL a strict dictionary containing only unique entities, since individuals can appear multiple times in homonym permutations.


* * Output: Lightweight file containing only the unified metadata per entity, ensuring I/O efficiency for the following steps.




* processamento06 embeddings.ipynb
* * Objective: Targeted lexical treatment for the vectorization step.


* * Operations: Isolates the textual categorical variables (professions, birthplaces, addresses, and nationalities) and executes parsing routines to remove prefixes inserted during extraction (e.g., "Occupation:", "Birthplace:").


* * Output: Consolidated file (`embeddings.csv`) containing only the pure semantic data, ensuring that noise does not interfere with the subsequent generation of vector representations.





### Phase 3: Modeling, Training, and Statistical Inference

The final phase consolidates the evaluation of the proposed methodologies, applying cross-validation, stipulating heuristic baselines, and training machine learning architectures for ranking, concluding with the statistical validation of the results.

* processamento07 splits.ipynb [CRITICAL COMPONENT]
* * Objective: Formulation of the experiment design and sampling.


* * Operations: Executes the "explosion" process of the homonym lists, transforming hierarchical data into a relational tabular format of the pairwise type (Target vs. Candidate). Generates the response variable (categorical label 1 for correct identification and 0 for divergence). The algorithm applies stratified data partitioning into 5 independent sets (K-Folds), ensuring strict segregation between Training, Validation, and Test partitions to prevent data leakage and bias in the metrics.


* * Output: Vectorized files per split, ready for consumption by optimization algorithms.




* processamento08 heuristica.ipynb [CRITICAL COMPONENT]
* * Objective: Establishment of the unsupervised Baseline.


* * Operations: Implements a deterministic ranking system based on logical rules. The algorithm evaluates match degrees based on relational attributes (such as kinship coincidence - fathers, mothers, siblings) and temporal tolerance (differences in birth date). From these empirical rules, it computes the initial performance metrics (Mean Reciprocal Rank - MRR, and Recall@K for ranges from 1 to 20).


* * Output: Base metrics matrix that acts as a minimum acceptance threshold for the performance of subsequent machine learning models.




* processamento09 modelos.ipynb [CRITICAL COMPONENT]
* * Objective: Training of Learning-to-Rank Algorithms and Interpretability Analysis.


* * Operations: Constitutes the algorithmic core of the experiment. Processes the pre-processed partitions and trains optimization architectures targeted at ranking problems. The environment supports the evaluation of Logistic Regression, XGBoost Ranker, and LightGBM Ranker. Concurrently with the measurement of MRR and Recall@K per fold, the module instantiates the SHAP (SHapley Additive exPlanations) library to extract the degree of explainability of the tree-based models. This allows quantifying by percentage the marginal contribution of attributes such as `address`, `age`, `profession`, and `relationship_indicators` in the final decision function.


* * Output: Optimized model weights, final tabulation of ranking metrics per fold, and feature importance matrix (SHAP values).




* processamento10 comparação.ipynb
* * Objective: Verification of statistical significance.


* * Operations: Conducts the final scrutiny of the experiment through statistical inference. Compares the resulting metric vectors of the proposed models (e.g., XGBoost Ranker vs. LightGBM Ranker) applying the Wilcoxon Signed-Rank Test. The test is configured unilaterally to assess whether the performance distribution of the dominant model is stochastically greater, rejecting the null hypothesis of equality motivated by stochastic sample variation.


* * Output: Conclusive report presenting the W statistics and the corresponding P-values, ensuring methodological rigor for the theoretical foundation of the scientific paper.

## Execution Parameters and Requirements

* Dependency Order: The project architecture makes asynchronous or out-of-order execution unfeasible. The standard output of a module acts as a critical input dependency for the subsequent component.
* Processing: Robust RAM allocation is highly recommended, particularly during the I/O routines of JSONL files and the instantiation of relational explosion matrices (Notebooks 01, 04, and 07).
* Computational Dependencies: The ecosystem is based on vector structure manipulation (`pandas`, `numpy`, `pyarrow`), classical engineering and modeling (`scikit-learn`, `xgboost`, `lightgbm`), and advanced evaluation methodologies (`shap`, `scipy`). Asynchronous search routines and extensive transformations are monitored via `tqdm`.
